## Summary of what is settled

1. Body: the character on foot is a lux::CollisionPencil (a cylinder with a conical tip, built from the
   form's height and radius), in a physics body, not a sphere or a capsule. Its sizes come from the
   avatar's height and radius. Settled [game]. Its masks: 0x45 for the player, 0x0D for an AI-controlled
   character [game]. Which bit is which is [assumed] (see question 1).
2. The step: the pencil is a holder of the world's physics. Contacts are generated by the swept pair test
   (the pencil sweep, 005e2620 and the GJK kernel 005c9eb0 / 00616ed0), then resolved by 006e2c10. For a
   pencil against a STATIC world body, the response is: (a) a ground override: a contact on the ground
   layer below the pencil's bottom gets normal (0,0,+1) and skips the commit; (b) otherwise the simple
   path: slide the pencil's position along the contact, kill the approaching normal velocity (no
   restitution term) [game]. Step-up height and maximum slope: NOT found in these functions [game: none
   present in 006e2c10 lines 31-599]. "On the ground" versus "falling": NOT settled.
3. The ground snap 00737120 does NOT write the character height from its hit point in the code read.
   The hit point goes to FUN_00737720, which does not write the position; it returns a record or null
   [game]. So the "snap" is not the floor rule. The floor rule is the ground override in 006e2c10.

## 1. The collision body on foot

Source [game]: `pencil_avatar_create` (006e7b60) and `pencil_avatar_shape` (006e7e90), called from
`first_avatar_create` (00853550) for each avatar slot (i = slot index; body pointer at EDI+0x60+i*0x34).

Sizes [game], with h = the form height and r = the form radius, both passed in from the form data
(`first_avatar_create` gets them from the character's avatar pencil settings; the exact data field
names are not read here [unread]):

- cylinder part height = h - 5/11 h = 6/11 h. Stored as the pencil's first half-height term 3/11 h.
- tip gap (5/11 h, computed as param_2 * 5/11 where param_2 = 6/11 h, so the gap is 30/121 h).
- the pencil's second half-height term = 3/11 h + 5/22 h = h/2 (the total half height from centre to tip).
- radius = r (pencil slot +1).
- tip slope term = (3/11 h) / sqrt((5/22 h)^2 + r^2) (pencil slot +4).
- wrapper outputs: 0.8 * gap = 24/121 h (the ground-probe clearance; see climbing.md:28), gap = 30/121 h,
  and 3/11 h + gap = 63/121 h. Which of the three goes to which slot is taken from climbing.md:28 (the gap
  at +0x150, 0.8 gap at +0x140), not re-verified here [assumed].
- Robot check (from climbing.md): h = 5.4 gives gap 1.339, 0.8 gap 1.071.

Body creation [game] (006e7b60): `physics_body_create` (006e0ee0) with the identity matrix (DAT_00c02990..),
shape = the pencil, flags 0x284, mask word = (param 0x44 | 5) for the player, (0x0C | 5) for an AI, i.e.
0x45 and 0x0D. Right after creation the holder's +0x1d4 gets bit 0x1000 (the "avatar" bit used by the
response) [game]. The body's +0x50..+0x58 get the three values of param_4..param_6 [game].

Masks [game for the numbers, assumed for the bit names]: the 0x45 mask is the one the avatar's
contact sweeps use (007c84c0, 007c86a0 in docs/character-world-probes.md). The bit names used in
docs/collision-query-masks.md give: 0x45 = PLAYER_PUSH | AVATAR_PUSH | PUSH, 0x14 = GROUND | AVATAR_PUSH,
0x1d = GROUND | AI_PUSH | AVATAR_PUSH | PUSH, 0x0D = AI_PUSH | AVATAR_PUSH | PUSH [assumed: the bit values
0x40 PLAYER_PUSH, 0x10 GROUND, 0x08 AI_PUSH, 0x04 AVATAR_PUSH, 0x01 PUSH; settled by the enum in the
engine's data or by a test that sets one bit]. The response code tests bit 0x10 (GROUND) of the mask
word B+0x9c & A+0x9e (006e2c10 lines 44-49) [game].

Shape type: the pencil's shape-type slot 1 returns 8 [game] (006e8d20, `virtual_type_eight`).

## 2. What runs each step (0.032 s)

Chain [game unless marked]:

1. Character update: 0071dc20 `character_update` (animation exits before movement; movement not read here).
2. Holder placement: 006dbd30 `holder_set_affine` composes the avatar local affine and syncs the body;
   0052fbf0 composes the input with the holder's local avatar transform (docs/driving.md "physics handoff").
3. Pair generation (broadphase): 006e1bc0 builds the pair records from the holder matrices (+0x108..0x134)
   and calls the shape's vtable slots 8 and 0x10, then 005e3a50. Callers 006e2c10 and 006e5e00.
   [game] (ledger).
4. Hit collection: 005e3d50 walks the 121 bins (11 x 11) and calls 005e39a0 per object (ledger, [game]).
5. The pencil's swept support: 005e2620 `pencil_swept_support` (out_shape = transform(pencil support of
   v*Y, P), out_sum = out_shape + sphere support of rec0), bit-exact in 1200 cases
   (docs/collision-support-swept.md). The pencil support itself: 005aff10 `pencil_support` (tip at
   (0,0,+-P+8) if |v| * P+0xc < |vz|, else the base rim at z = +-h, radius P+0), 2000 emulator cases 0
   difference (docs/collision-support-2.md) [game].
6. The GJK ray cast vs the pencil: 005c9eb0 `ray_test_pencil`, support 005aff10, emulated
   (docs/collision-tests-emulated.md) [game].
7. The sweep kernel 00616ed0 (called from the sweep primitive family; the unpublished notes row P):
   a segment routine that tests the squared length of a segment against 0.0001, appends records of stride
   0x3c into a list capped at 0x12a = 298 entries (over the cap it writes -1.0 and returns 0), and calls
   006cbe80 for a point [game for those lines, lines 1-60 read; the rest [unread]]. The camera call
   005571b0 and the "CapsuleRenderNode" name in the census are NOT trusted (census label) [assumed].
8. Hit consumption: 006e2c10 (docs/collision-response.md). Drain (005e3da0), sort by time (00584e20,
   ascending [assumed]), per hit: time gate, masks, normal orientation, commit, contact generation
   (006e6a10, first 75 lines only), response. Loop until the drain is empty; no iteration cap.

Response for the pencil (A or B holder with +0x1d4 bit 0x1000) [game, from docs/collision-response.md
and re-read of lines 84-152]:

- Tolerance: 0.01, or 1.0 when a root has bit 0x10 (lines 93-99).
- GROUND OVERRIDE (lines 100-138): only when exactly one holder has 0x1000. If the mask B (or A) has 0x10
  and a root has 0x2000 (or mask 0x800), and the OTHER side's body pointer +0xa4 is null (a static
  object with no body), the contact height is compared with the avatar's bottom (006e9550
  `avatar_bottom_distance`: wrapper +0x54 times the up vector's length). If it is a hit: normal := (0,0,+1)
  or (0,0,-1) by sign, bVar10 := 0, and control goes to label 159 (no commit, no velocity change). This is
  the floor rule: a contact under the pencil's bottom is a floor; the pencil is not pushed sideways.
- Commit (lines 139-152): if the body guard holds (+0xa4 non-null, +0x38 byte == 0, +0x34 == 0.0), the
  pose is committed (006dc3b0). This is for a dynamic body.
- Separating test (159-170): if (vA - vB) . n >= 0 the contact is dropped. The time gate +0x244 is written
  before the test (C7 in collision-response.md).
- Simple path (lines 212-301, contact+0x1e8 == 0): if A is dynamic (+0xa4 body, +0x38 == 0), the frame is
  built (006deda0 [unread]), the position slides on A (lines 277-289), velocity from 00556c00 (ledger,
  [game]) and the approaching normal component is killed (291-298). Inelastic [game for the code, the
  velocity kill is the only term read]. For a static B (+0xa4 null) only A moves.
- Full path (400-599): inverse-mass and inverse-inertia terms, normal impulse lambda = -(relative normal
  velocity)/k clamped to >= 0, friction clamped at 0.333 per slot, scaled by contact+0x1bc (line 593).
  Not read in detail here.

Slope: no slope threshold was seen in 006e2c10. The only normal test is the ground override's "hit under
the bottom" and the sign of n. [game for the absence in the read lines; the contact generator 006e6a10
after line 75 is unread, so a slope rule may live there.]

Step-up: NOT FOUND. No step-up height appears in 006e2c10, 006e9550, or the pencil builders. The step-up
may be in the character's movement code or in 006e6a10 [unread].

On the ground versus falling: NOT SETTLED. The floor rule above gives the contact; no grounded flag was
found in the read code. The character's "+0xa4 / +0x38" latch in 00737120 is a per-character latch of
unknown meaning [assumed].
